# 开发任务的验证与 GitHub 交付

Myrmecia 将“Agent 结束运行”“代码检查通过”和“人工接受交付”分开处理。
任务状态为 `done` 不意味着代码正确、远程 CI 通过，或可以跳过代码审阅。

## 开发 Agent 的测试要求

默认 Dev Agent 的 implement/refactor 步骤必须执行真实测试。测试失败、
超时或找不到可用测试命令都会阻止该步骤通过，不再用 `true` 替代测试。

命令发现依次检查项目根目录的真实 `scripts.test`、Go/Rust/Python 项目
标记，以及独立 Node 测试文件。Monorepo 没有根测试脚本时，不会把各个
包里的测试文件拼成一个不可靠的命令。此时请选择具体包目录，或者在
任务验收条件中提供必需的包级测试命令，例如：

```text
pnpm --filter @myrmecia/server test
```

Dev 步骤只能使用持久化任务验收条件中的必需测试命令作为覆盖项。
`build`、`lint` 和 `typecheck` 不能替代该步骤的测试。
项目自己的测试脚本仍可能是空测试或覆盖不充分；退出码为零不是
充分的正确性证明，审阅者需要检查测试内容。

## 可提交的验证命令

GitHub 交付验证和 `test_command` 验收条件接受有界的命令白名单，例如：

| 类型 | 示例 |
| --- | --- |
| JS/TS 项目 | `pnpm test`、`npm run build`、`yarn lint` |
| Monorepo 包 | `pnpm --filter @app/server test` |
| Python | `python -m pytest tests -q`、`pytest tests -x` |
| Go | `go test ./... -race -count=1` |
| Rust | `cargo test --workspace`、`cargo test --package app` |
| Node | `node --test tests/example.test.js` |

参数以独立、安全引用的 token 执行。任意 shell 片段、管道、重定向、
命令替换、安装/部署命令、绝对路径与 `..` 路径不在此入口的白名单中。
白名单不是操作系统隔离：`npm test` 或 `cargo test` 仍会执行仓库的代码，
可能修改文件或访问当前执行环境。只对可信项目运行，并检查 Settings
显示的实际执行环境。GitHub 发布记录准确标明所运行的命令；只运行
build/lint 不能宣称测试套件已经通过。

## Teams 中的 GitHub 修复交付

1. 等待根任务及所有层级的子任务结束。运行中的、失败的或已拒绝的
   执行，以及失败/不可用的必需验收证据，都会阻止发布。
2. 打开完整变更预览，检查全部文件，包括未跟踪的新文件。预览记录
   文件内容哈希、模式、HEAD、分支及任务证据。
3. 明确确认后执行“验证当前文件版本”。验证有独立 Task/Execution、
   保留的输出产物和文件版本绑定，不会向模型发送任务。
4. 检查验证证据，勾选接受已审阅交付，并输入 `CREATE PR`。
5. 创建 PR 只提交完整审阅清单，不使用 `git add -A`。如果没有上游
   写权限，必须另行允许创建或复用当前 GitHub 账户的 Fork；Fork 的
   upstream parent 和 push remote 都要匹配已确认的仓库。

本入口不支持从一个脏工作树里随意挑部分文件发布：未提交文件可能
参与测试，使“测试通过的工作树”和“提交的文件”不一致。先在修复
checkout 中整理无关修改，再审阅完整清单。

敏感路径、可能的密钥、符号链接、二进制文件，以及超过预览上限的
变更会阻止此自动发布入口。当前预览上限为 150 个文件、每个文件
1 MiB 和总 patch 500,000 字符。需要单独的人工交付路径处理这些情况。

验证期间文件发生变化、命令改变、刷新审阅或切换修复会话后，
旧的验收确认不可复用。发布还会检查 staged blobs、commit tree 和
实际 push URL，防止 Git filters 或远程地址变化改变已审阅的交付。

## 中断与恢复

“停止验证”请求取消命令，不保证撤销已发生的脚本效果，也不会把
晚到的成功结果覆盖到已取消的任务上。

提交、Fork、push 或 PR 创建的响应丢失时，持久化记录会保留阶段，
不会自动再执行一次。必要时使用“核对既有结果”：

- 首先自行确认相关进程与副作用已经停止，并检查工作区/远程状态。
- 核对操作读取已有 commit、远程 branch 或 PR 状态，不重放原命令。
- 无法证明结果时仍会阻止继续。未知的工具历史不会被改写成成功。
- 确认可继续时复用已有 commit/PR，并更换操作令牌，阻止旧结果推进。

后端重启后不会把人工验证任务误派发给模型。恢复发布要求同一
GitHub 账户和同一发布 payload；不要切换身份后盲目重试。

## 工作区搜索与运行环境

`grep`/`search` 不再只搜索 JS/TS，支持其他源码语言、配置和文档，
默认采用字面量搜索。符号链接、依赖目录和排除的敏感路径不会被读取。
扫描/匹配/输出达到上限时会明确提示 partial，不能把局部无匹配
当作全仓库证明。正则表达式在有内存与时间限制的 Worker 中处理
已经授权读取的内容，避免病态正则长期阻塞主服务。

Settings 展示当前生效的 runtime、工具执行环境、鉴权、队列与恢复
边界。源码实现了 Runtime V2 或 Docker execution world，不意味着
当前已经启用它们。本轮修复不会自动启用这些部署选项、安装 Redis/
Docker、改变账号，或扩大任务权限。

原生 Codex executor、真实模型开发对照基准、远程 CI 和生产环境
安全验收仍属于独立集成/验证，不由这套本地测试门禁替代。

## 开发任务的设计与交付协议

### 同一执行中的宿主阶段（2026-10-16）

完整系统和新 UI 使用宿主推进的独立请求，而不是让模型在一个 SDK
内部循环里自行宣布全部完成：

`design → core → ui → host verification → delivery`

纯后端使用 `design → implementation → host verification → delivery`；
仅界面设计/开发无需额外 core 阶段。阶段变更使用新的、带阶段身份的
system 上下文；保留原请求、真实队列追问和宿主证据，不把模型摘要
升级为用户指令。V2 journal/checkpoint 与 runState 都记录阶段。
存在未知副作用或进行中的验收时不能盲目恢复/重放。

所有阶段共享原 task/execution、累计 Token、轮数、工具计数、持久化
任务预算和绝对 deadline。阶段本身还有请求上限（全任务额度的
design 25%、core 40%、ui 40%、后端 implementation 60%、repair 25%、
delivery 8%）；这些是各阶段上限，不是新增配额或保留额度，总使用量
始终受原任务上限约束。用完额度/时间会停止，不换模型或新建子任务
来重置预算。Runtime V2 的 provider driver 也转发 SDK contextBudget。

设计阶段只允许原有权限内的读取和设计 JSON 写入；有效设计移交后
冻结其哈希。core/UI 结束须有真实声明文件。验收暂只支持已经由
operator 明确授权、绑定 workspace root 和 package.json 哈希的
**精确 `npm test`**；不自动扩大到任意 shell、多语言命令或新脚本。
已有开发 writer 使用其本人的有效租约运行验收，不借用其他任务锁。
验收继承原取消信号、剩余执行时间、工具耗时和授权过期时间。

真实测试失败可进入 **一次** repair；repair 只读文件和修改已声明的
实现源文件，不可执行 shell、改设计、测试或配置。第一次验收前冻结
非实现测试/配置/支持文件的哈希，重测/交付再次核对；测试期间改写
实现也会被拒绝。测试变更需要人工核对并重新界定范围。
为保证修复不能修改测试入口，即使设计把 Node 测试脚本声明为实现
文件，该入口仍会被保护。内联 repair 暂只接受可有界解析的
`node <入口>` / `node --test <明确路径或简单 glob>`；无参数的
Node 默认发现、复杂 runner、loader/config 或无法判断入口的脚本
失败后要求人工重新界定范围。
没有授权、脚本哈希变化、零用例、无可验证输出、超时或进程退出未知，
都会停止，不能作为“修复测试”或通过信号。

delivery 为只读并核对已验证文件哈希。验收后出现新追问会使旧
receipt 不能直接交付，需要重新界定验收。独立 QualityLoop 仍可
拒绝交付，但不会再为阶段任务自动创建新 Fix 子任务绕过一次修复
上限。阶段/自测通过不等于独立 QA、浏览器、视觉、远程 CI 或人工
接受；当前阶段记录始终明确 `browserAcceptance: unverified`。

适用于 `dev` / `developer` / `frontend` / `fullstack` / `full-stack`
角色。任务意图分型是启发式交付策略，不是权限来源：

| 当前请求 | 要求 |
| --- | --- |
| 新建完整系统、应用或平台 | `docs/development-plan.json`；涉及前端时还需 `docs/ui-design.json` |
| 新建或重设计界面、页面、看板 | `docs/ui-design.json` |
| 小修复、明确单文件修改 | 内联简要设计，不强制新增授权范围外的文档 |
| 只读审查或验证 | 不强制写设计文件，不要求以写入中断探索 |
| 服务端生成的人工追问 / 质量循环 Fix 子任务 | 按当前追问或修复范围判断，不把旧的完整系统目标再当新建项目 |

纯后端/API、CLI 和库任务不强制 UI 设计。QA、Reviewer 和内容角色
不套用此协议。自定义 Skill 与默认 Dev Skill 均追加宿主协议；
编辑 Skill 不能关闭工具或完成门禁。
明确的只读审查/验证请求跳过包含代码写入/实现阶段的开发 Skill 与
自动 Skill 匹配，并追加“仅检查、不改代码”指导，不自动运行写测试/
实现阶段；已有真正只读的分步 Skill 及其恢复边界保持可用。
此指导也不是对任意工具副作用的额外沙箱保证；原任务授权仍须生效。

### 先设计，再开始实现

有设计要求时，先用 `file_write` 写真实 JSON。系统计划包含：

- `schemaVersion: 1`、准确的 `taskId`、`summary`、`users`；
- `flows` 中的名称与至少两个流程步骤；
- `modules` 中的职责、接口与相对路径 `sourceFiles`；
- `dataStrategy`；
- `acceptance` 中的验收 ID、描述和证据类型；
- 至少两个 `milestones`，各自包含交付物和检查方式，以及 `risks`。

UI 设计包含准确的任务 ID、视觉方向、三色基调、字体与层级、
导航/主操作/桌面/移动布局、页面用途/组件/源文件、每页的
loading/empty/error/success 状态、交互与键盘/焦点/对比度/
减少动效规则。详细字段以
`packages/server/src/agents/development-workflow.ts` 的 schema 为准。

设计文件限 32KB，必须为严格 JSON；不接受 Markdown 代码围栏、
陈旧任务 ID、占位文本或伪造的“验收通过”字段。重要描述至少五个字符。
声明的源文件须为工作区内相对路径的源码，不接受隐藏路径、
父目录穿越、反斜杠路径或归档文件。

缺少设计时，业务写入、Shell 和未知副作用工具会被拦截。宿主已知
的只读内置工具可以用于必要的文件和参考资料查阅；未知 MCP 工具
需要先完成设计。该判断不会把未授权工具加入 allowlist。
连续三次设计拒绝会明确停止，不自动重试整个任务。
已有设计文件仍须在本次执行里先读取再改写；原读写授权、参数和
read-before-write 门禁保持生效。

### 避免无效探索耗尽预算

从上一次成功写入开始，连续六次只读探索给模型可见提醒，
第十次再次提醒；十二次完成/已预留的探索后阻止下一次探索。
不同文件、查询、分页 offset 或 SDK 同一请求内的回调同样计数。
并发回调同步预留计数，不因同时发出多次读取绕过上限。

只有实际成功、非空的 `file_write` 或内容发生变化的 `apply_patch`
重置计数。失败补丁、空写入、原样补丁和反复运行旧测试不算进展。
分页结果保留原内容、offset/hash 等字段；宿主提醒单独附加，
不会把原始工具收据改写成模型“已经完成”的证据。

### 完成检查与证据边界

运行结束前，除 `needs_input` 澄清外，统一检查必需设计及其中声明的
源文件是否真实存在、非空、大小受限且没有符号链接/越界。设计绑定
本次 taskId；源码限 1MB。记录文件 SHA-256 与
`design_schema_and_declared_files` 证据范围。

缺失产物产生 `DEVELOPMENT_DELIVERY_INCOMPLETE`，保留部分输出并将
执行记为失败，不得仅靠一句“已完成”结束。新设计/探索/交付门禁
错误不盲目自愈重跑。

这些检查不验证设计是否美观、代码是否与设计语义一致、模块是否
真的集成或测试是否通过。既有真实测试、QA/Review、浏览器流程和
人工视觉验收依然各自需要证据；没有浏览器能力时必须标记未验证。
文件/schema 检查通过不改变运行的 `acceptance: pending`。

Copilot 每个阶段内部仍使用 SDK 循环；宿主在独立请求边界推进阶段，
并通过工具回调、checkpoint 与最终交付检查约束进度。SDK 内部用量
只能在事件到达后观察，可能在中断前超过阶段额度，不是每次隐藏模型
调用前的硬预付限额。原任务 token、timeout、权限与发布确认不变。

### 真实试验发现的运行时保护缺口

文件读取、写入、补丁、目录及 Shell 操作在共享中间件与直接工具
执行入口验证服务器自有参数 schema。缺少 `path`/`content` 的写入、
错误字段类型和冲突的历史别名不得变成空文件写入或工作区目录操作。
明确传入 `content: ""` 仍可创建空文件，但不算开发进展。历史
`file_path` 别名同样受本次执行的 read-before-write 门禁约束。
这不授予工具权限，也不执行第三方/模型提交的 schema。

SDK 请求中途失败时，已接收的用量事件保留为已观察下界，记录到
进度、失败调用统计及 decision ledger。请求的最终用量尾部仍未知：
保守预算 hold 不得少于已观察下界，不标为完整结算、不退还不明
用量，也不把 `token_budget` 等原始失败原因改成成功。
未知账目不能依据错误字符串解析数字来“补记”。这轮历史失败不会
被修改；新保护只应用到后续运行，并同时覆盖 legacy/V2 请求路径。
